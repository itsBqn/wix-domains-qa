# Wix Domains QA - Home Assignment

This repo is my QA home assignment for the Wix Domains team.
It tests the four public "doors" that answer "Can I get this name?":
the domain storefront, the Business Name Generator, the WHOIS lookup and the public Domain Search API.

## Setup and run (Windows)

1. Create a virtual environment:
   ```
   python -m venv .venv
   ```
2. Install the packages:
   ```
   .venv\Scripts\python -m pip install -r requirements.txt
   ```
3. Install the Chromium browser for Playwright (only once):
   ```
   .venv\Scripts\python -m playwright install chromium
   ```
4. Create a file named `.env` in the repo folder with your own values:
   ```
   WIX_API_KEY=<your account-level API key>
   WIX_ACCOUNT_ID=<your account ID>
   ```
   `.env` is in `.gitignore`. Never commit it.
5. Run all tests with one command:
   ```
   .venv\Scripts\python -m pytest -v -rxXf
   ```

## What the results mean

Expected result: **29 passed, 4 xfailed**.

An xfail is a test that fails on purpose because of a known problem. Each one is a finding (see FINDINGS.md, F5).
The xfails are `strict`, so if Wix fixes the problem, the test turns red and tells us to update it.

- `test_api_05_no_authorization_header_is_rejected`: the API answers 200 with no Authorization header. The docs say a key is required.
- `test_api_06_wrong_key_is_rejected`: the API answers 200 with a wrong API key.
- `test_api_07_no_account_id_header_gives_clear_error`: the API answers 200 with no `wix-account-id` header.
- `test_e02_impossible_name_gives_400` (64-character name): the docs say the maximum is 63 characters, but the API accepts 64.

## Why I automated what I did

- **API first:** it answers the core question directly, it is fast and stable, and it does not depend on the UI.
- **One web door (the storefront):** the brief asks for at least one web door, and the storefront is the main one. One test compares it with the API (the doors must agree).
- **Manual for the rest:** the Business Name Generator output is generated by AI and changes on every visit, and WHOIS depends on outside RDAP servers. Automated tests there would be flaky.

## My quality strategy for Wix Domains in 5 lines (draft)

1. The core risk is a wrong availability answer, so the doors must always agree with each other.
2. Test edge cases first (messy input, non-English names, special characters), because that is where users get wrong answers.
3. Automate at the API level, where tests are fast and stable, and keep a few UI tests for the main flows.
4. Assert only on stable things (status codes, fields, rules), never on prices or generated suggestions.
5. Check that the API matches its docs and that errors are clear and safe, because developers build on them.

# Test Plan

The four doors answer one question: "Can I get this name?".
This plan is based on ARCHITECTURE.md (what I saw in DevTools) and the brief.
Expected domain behavior from the brief (prices by location, generated suggestions,
redacted WHOIS, TLDs Wix doesn't sell, and so on) is **not** treated as a bug.

## 1. Scope

| In scope | Out of scope |
|---|---|
| Public API: `check-domain-availability` (with my own key) | Checkout and payment (never complete a purchase) |
| Storefront: search, availability message, suggestion list | Load, stress or performance tests |
| Business Name Generator: names, then domains for a picked name | Exact prices and currency values |
| WHOIS page: registered and unregistered domains | The exact list of suggestions (it is generated) |
| The doors agree with each other on availability | Other accounts and private Wix pages |
| Bad, messy and non-English input | The developer docs site itself |

## 2. Approach

| Area | How | Why |
|---|---|---|
| Public API | Automated (pytest + requests) | Fast, stable and cheap. It answers the core question directly. |
| Storefront | Automated (Playwright, Chromium), one main flow | The brief asks for at least one web door. The storefront is the main door. |
| Business Name Generator | Manual, exploratory | Output is generated by AI and changes on every visit, so automation would be fragile. |
| WHOIS page | Manual, exploratory | It depends on outside RDAP servers. Automated tests would fail when they are slow. |
| Cross-door checks | Manual, plus one automated API-vs-storefront check | Comparing doors is the highest risk, so at least one check runs every time. |

Rules for the automated tests:
- Assert only on stable things: status codes, field names, `available` for known domains, and that a domain has a TLD.
- Do not assert on prices or on which suggestions appear.
- Keep API calls low (a few hundred in total). No loops over many domains.
- The API key and account ID come only from `.env`. They are never printed.

## 3. Edge cases first

Edge cases come first because the happy path ("search `mybakery.com`, get an answer") is the part
most likely already tested by the team. Edge cases are where users get a wrong answer.

| ID | Edge case | What I check | Why (user impact or risk) | How |
|---|---|---|---|---|
| E-01 | **The doors disagree** | Same domain on the storefront, WHOIS and the public API at the same moment. All give the same `available` answer. | This is the core question. If one door says "free" and another says "taken", the user can't trust Wix. | Auto (API vs storefront), manual (WHOIS) |
| E-02 | **Bad or messy input** | Uppercase (`MyBakery.com`), spaces at the start or end, `www.` or `https://` in front, no TLD (`mybakery`), 1-letter name, 63-character label (the maximum), 64-character label (too long), hyphen at the start or end, characters like `_` or `!`. Expected: a clear error, or the same answer as the clean form. Never `available: true` for a name that can't exist. | Real users type this way. A wrong "available" answer leads the user to try to buy a name that can't be registered. | Auto (API), manual (storefront) |
| E-03 | **Non-English names (IDN)** | A Hebrew name, and the same name in punycode (`xn--...`, the ASCII form). Both get the same answer. | Wix serves Israel. Both forms are the same domain. Different answers mean wrong results for Hebrew-speaking users. | Auto (API), manual (storefront) |
| E-04 | **WHOIS on a domain nobody owns** | The page says the domain is not registered. No error text and no broken page. | Users often use WHOIS to check if a name is free. A free domain has no RDAP data, so this path is easy to miss. | Manual |
| E-05 | **Business names with special characters** | The generator gave names like "Crust & Crumb" and "Baker's Delight". Pick them and check the suggested domains. `&` and `'` must not end up in a domain. | A domain with `&` or `'` can't exist. Showing one is a broken offer and a dead end for the user. | Manual |

**Next in line: premium domains.** Check that `premium: true` from the API matches the premium
label and price in the UI. A higher price for a premium domain is expected. A wrong or missing
label is not, because the user sees the wrong price.

## 4. Test cases by door

The edge cases above are not repeated here.

**How I set priority:**
- **P1:** the user gets a wrong availability answer, the main flow breaks, or a security problem.
- **P2:** wrong or broken information on screen, or a secondary flow breaks.
- **P3:** small display issues, wasted calls, slow but working.

**How I simulate errors (manual):** DevTools "Block request URL" to make a call fail,
and DevTools "Override content" to return an empty or changed response.

| SF-06 | Search with an empty box | Negative | P2 | Manual | Should show a clear hint, not an empty or broken result. |
| SF-07 | Search a TLD Wix doesn't sell | Negative | P2 | Manual | Not selling it is expected. The message must say so clearly, not "taken" or "available". |

## 5. What I left out on purpose

| Left out | Why |
|---|---|
| Completing a purchase or reaching checkout | Forbidden by the rules. |
| Load and performance tests | Forbidden by the rules, and the API call budget is small. |
| Exact prices and currency | They depend on location and promotions. Asserting them would make tests flaky. |
| Exact suggestion lists | They are generated and change between calls and doors. |
| Testing from other countries (VPN) | All testing is done from Israel. Prices, currency and some suggestions may differ in other countries. Testing from other countries is out of scope. |
| Browsers other than Chromium, mobile, accessibility | Not enough time in 3 hours. These are next week's work. |
| Business Name Generator automation | AI-generated output, too fragile to automate in the time budget. |

## 6. Main risks

| Risk | Impact | What I do about it |
|---|---|---|
| The doors may not use the same backend (`www.wix.com` vs `www.wixapis.com`, not verified yet) | Doors could disagree on availability | Edge case #1 compares them directly. |
| Availability is a point-in-time answer | A "free" test domain could be taken later and the test fails | Use long random names for "free", and well-known names for "taken". |
| WHOIS depends on outside RDAP servers (Verisign, registrars) | The page breaks when they are slow or down | Manual testing only. Note it as a risk, not a Wix bug. |
| Bot protection on wix.com | UI tests may be blocked | Keep UI tests few and slow. Report it if it happens. |
| Generated content (names, suggestions) | Tests that check exact values become flaky | Assert only on shape and rules, never on exact values. |
| API call budget (a few hundred in total) | Running tests too often could go over the limit | Few API tests, no loops over many domains. |
